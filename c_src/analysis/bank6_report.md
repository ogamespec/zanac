### 1a. Anomalies

* **Labels out of address order**: none. The 856 labels are strictly increasing in address (checked).
* **Overlapping labels / duplicate addresses**: none. No two labels share an address (checked).
* **Aliases (same address, different name)**: none inside bank6. Cross-file aliases exist and the
  generator must not treat them as distinct objects: `src/bank6_api.asm` re-declares the 12 bank6
  thunks (`j_game_logic_processing equ $8000` … `j_check_enemy_overflow equ $8021`), and `src/vars.asm`
  declares two names for one byte at `$86` (`byte_86`/`unk_86`) and two for `$CB` (`byte_CB`/`unk_CB`).
* **`tab_18619_lo`/`tab_18674_hi` are read one byte *before* their labels** (`LDA $8618,Y`, `LDA $8673,Y`),
  and every `switch_case` table is read as `table[index*2+1]`/`[+2]`; see §2. Treat the label address as
  the base of `entry[0]`, and the code's literal as `label-1`.
* **`locret_18806` ($8806) is a multi-role byte**: it is the `RTS` that performs the enemy dispatch *and*
  the value pushed on the stack as the "return address" for the dispatched handler. Both executions of
  the same `RTS` (opcode `$60`) are intentional (§2.2).
* **Dead/alternate code hidden inside a data table**: bytes `$8184`–`$818B` are emitted as the last two
  rows of `tab_18144` (`.BYTE $85,$10,$84,$11` / `.BYTE $A9,0,$F0,7`) but disassemble as
  `STA $10 / STY $11 / LDA #0 / BEQ $8193`, i.e. an alternate entry into `slope_div` ($818C).
  No instruction in bank6 references `$8184`–`$818B` and the table is only indexed with `Y = slope*4`
  (`slope` 0–15 → rows 0–15, `$8144`–`$8183`), so those 8 bytes are unreachable as data *and* as code
  in this bank. *(Interpretation/inference, not proven: dead bytes or a removed entry point.)*
* **46 of 218 procedures have no terminating `RTS`/`JMP`/`RTI`** — see §3.1.

## 2. The enemy dispatcher

### 2.1 `game_logic_processing` ($87C7, L1751) — the slot loop

* `LDA $528,X / BEQ loc_18807` (L1779–L1780) — `$528` = object type; bit 7 = "spawned".

### 2.2 The dispatch itself — stack + `RTS`, **not** `JMP (vector)`

Exact source (`src/bank6.asm` L1777–L1796):

```asm
L1777  $87EE               loc_187EE:
L1778  $87EE  86 40        STX     $40
L1779  $87F0  BD 28 05     LDA     $528,X
L1780  $87F3  F0 12        BEQ     loc_18807
L1781  $87F5  29 7F        AND     #$7F
L1782  $87F7  A8           TAY
L1783  $87F8  A9 88        LDA     #$88
L1784  $87FA  48           PHA
L1785  $87FB  A9 06        LDA     #6
L1786  $87FD  48           PHA
L1787  $87FE  B9 73 86     LDA     $8673,Y
L1788  $8801  48           PHA
L1789  $8802  B9 18 86     LDA     $8618,Y
L1790  $8805  48           PHA
L1792  $8806               locret_18806:
L1793  $8806  60           RTS
L1794  $8807               
L1796  $8807               loc_18807:
```

Mechanism (this is the single most important thing to get right):

1. `LDA #$88 / PHA`, `LDA #6 / PHA` pushes `$8806` onto the stack (L1783–L1786, `$87F8`,`$87FB`,`$87FC`,`$87FD`).
2. `LDA $8673,Y / PHA` pushes the **high** byte of the handler address (L1787, `$87FE`).
3. `LDA $8618,Y / PHA` pushes the **low** byte (L1789, `$8802`).
4. The next byte, `locret_18806` = `$8806`, is an `RTS` (opcode `$60`, L1793).
   `RTS` pops low, high, **adds 1**, hence `PC = (hi<<8|lo) + 1`.
5. Therefore the two tables store **`handler_address - 1`**, and the real entry is
   `(tab_18674_hi[t]<<8 | tab_18619_lo[t]) + 1`.
6. The pushed `$8806` is still on the stack. When the handler finally executes its own `RTS`,
   it pops `$8806`, adds 1 and resumes at `loc_18807` ($8807, L1796) — the slot-advance code.

Consequences for C translation:

* The dispatcher is a **computed `RTS`**, equivalent to a `switch (type)` whose cases are the
  `enemy_type_*` functions, with the "call" being a *tail jump* that keeps one stack frame.
  Each handler must execute **exactly one** `RTS` net (directly or by falling into a shared tail).
* `enemy_erase_and_continue` ($82FA, L649) does `PLA`×4 and then falls through into `enemy_erase`.
  The four discarded bytes are the **two nested `JSR` frames the handler left above the dispatch
  frame** (`handler → JSR process_enemy_flags_sprites → JSR process_y_speed`, or the same with
  `JSR sub_18347` in place of `process_y_speed`), *not* the dispatch frame. `enemy_erase`'s `RTS`
  then pops `$06/$88`, adds 1 and resumes at `loc_18807` ($8807): "erase this object and continue
  with the next slot". **Hard precondition: exactly 2 nested `JSR` frames**; at any other stack
  depth the unwind silently lands somewhere else. All the other `PLA` unwinds in the file are the
  same idea with 1 frame (see §3.3).
* `Y` is the type (`$528,X AND #$7F`); `X` is the slot. `A` carries the raw type into `enemy_prng`.
* `RTS`+1 also means **the tables never contain a plain address**; a C port should store real
  addresses and index `type-1` (type 0 = empty slot, so the tables are 1-based and the code reads
  `$8618,Y = tab_18619_lo[Y-1]`).

Parameter passing through the return address:

* **`switch_case`** (`$C7CF`..`$C7E5` in bank 7) — pops the caller's return address to find its own
  inline table (§2.7). Every `JSR j_switch_case` is followed by 7–8 `.WORD`s.
* **The dispatcher** — pushes the value `$8806` that the *callee's* `RTS` will consume (§2.2).
Stack-frame arithmetic common to all of them. At handler entry the stack (bottom → top) is
`[R_call, $88, $06]`, where `$06/$88` is the value pushed by the dispatcher (L1786/L1784) and
`R_call` returns to bank 7. A nested `JSR` pushes 2 more bytes. `PLA` removes bytes from the top,
i.e. from the *innermost* frame. So:

| helper | unwinds | remaining top | consumed by | effective result |
|---|---|---|---|---|
| `enemy_erase_and_continue` ($82FA, L649–L654) | `PLA`×4 = 2 frames (`process_enemy_flags_sprites` + `process_y_speed`, or + `sub_18347`) | `$06/$88` | `enemy_erase`'s `RTS` | erase slot, resume slot loop at `loc_18807` |
| `sub_1876A` `loc_18779` ($8779, L1641–L1643) | `PLA`×2 = 1 frame (its own `JSR`) | `$06/$88` | `JMP enemy_erase` → `RTS` | erase slot, resume slot loop |
| `sub_19CAB` ($9CB0, L5589) | `PLA`×2 = 1 frame (its own `JSR`) | `$06/$88` | `sub_19CAB`'s final `RTS` | finish `sub_19CAB`, then resume slot loop; the calling handler is abandoned |
| `decrease_enemy_health` ($A2B6, L6565–L6569) | `PLA`×2 = 1 frame (its own `JSR`) | `$06/$88` | its own `RTS` at `$A2B8` | resume slot loop; the calling handler is abandoned. Callers test the returned Z flag first (e.g. `enemy_type_90` L10272–L10274) |
| `sub_1B87F` `loc_1B88C` ($B889, L10307–L10309) | `PLA`×2 = 1 frame | `$06/$88` | `RTS` | resume slot loop |
| `sub_1B87F` `loc_1B89B` ($B89B, L10327–L10330) | `PLA`×2 = 1 frame | `$06/$88` | `JSR sub_18788` then `JMP enemy_erase` → `RTS` | erase slot, resume slot loop |

Because `$06/$88` is the *innermost* two bytes above `R_call`, **none of these unwinds ever returns
above the dispatcher**; they all land on `loc_18807` ("next object"). Getting the depth wrong
shifts the `RTS` target by one frame. A C port should model each of them as an explicit "abort this
handler and continue the slot loop" control transfer (plus the erase), not as a normal return.

### 3.4 Self-modifying code

**None.** No instruction in bank6 writes to any address `>= $8000`: there are exactly 0
`STA/STX/STY/INC/DEC/ASL/LSR/ROL/ROR` with an absolute operand `>= $0800` (see §5).
The apparent "self-modification" is the *computed `RTS`* of §2.2/§2.7, which modifies the PC via the
stack, not via memory. No code writes to `$C000`+ either, so there are no bank-switch writes.

## 5. Memory writes outside `$0000`–`$07FF`

**There are none.** Every `STA/STX/STY/INC/DEC/ASL/LSR/ROL/ROR` in the file was checked in both
addressing forms:

* absolute literal operands (e.g. `STA $460,X`) — **0** sites with a target `>= $0800`;
* named operands resolved through `vars.asm` / `bank6_api.asm` / `bank7_api.asm` / `nesregs.asm`
  (66 such writes) — **0** resolve to `>= $0800`.

In particular:

* **No PPU/APU/joypad writes.** `PPU_CTRL_REG1`…`JOYPAD_PORT2` (`src/nesregs.asm`) never appear in
  bank6 (0 matches for `PPU_`/`APU_`/`JOYPAD`). All hardware access goes through the bank-7 thunks
  (`j_ppu_*`, `j_apu_*`, `j_clear_oam_buffer`, `j_clear_screen`, `j_pad_read`, …) — §6.1.
* **No bank-switch writes.** Nothing writes to `$8000`–`$FFFF` (and nothing writes to `$6000`–`$7FFF`).
* **No OAM-DMA/stack-register direct writes** (`PPU_SPR_DMA`, `$4014`) — bank 7 owns OAM DMA.

The RAM the code *does* use (all inside `$0000`–`$07FF`, from `src/vars.asm`) is:

| range | user |
|---|---|
| `$00`–`$FF` | zero page: temporaries (`$10`–`$19`), pointers (`$18/$19` meta-sprite ptr), loop/index bytes, `$40` current slot, `$49`/`$47` sound counters; `$7E` PRNG state |
| `$100`–`$1FF` | scores (`$17D`, `$183`), palette update (`$144`/`$145`), HUD counters (`$19A`/`$19B`), `$171`/`$174`… |
| `$200`–`$2FF` | OAM buffer (`$200`+) — written here, DMA'd by bank 7 |
| `$300`–`$3FF` | APU engine state (`$300`+) — written here, consumed by bank 7 |
| `$400`–`$4FF` | background/scrolling engine state, plus a sprite-descriptor queue at `$460`+ |
| `$500`–`$7FF` | 26-byte object arrays: `$528` type, `$542` Y, `$55C` X, `$576` sprite id, `$5C4`/`$5F8`, `$612` Y-speed, `$62C`/`$646` X-speed, `$660` flags, `$67A`, `$694`, `$6AE`, `$6E2` chase timeout, `$6FC` chase counter, `$716` chase initial, `$74A` slope, `$764` health, `$77E`, `$798` |
| `$0100`–`$01FF` | 6502 hardware stack — heavily manipulated by the dispatch/switch/unwind tricks (§2.2, §3.3) |

**The only "writes above $07FF" in the whole design are the JSR/RTS/PHA/PLA stack traffic** that the
dispatcher, `switch_case` and the unwind routines rely on. A C port must model the exact stack
delta of each procedure, because `enemy_erase_and_continue` and the `PLA/PLA` unwinds depend on it.
